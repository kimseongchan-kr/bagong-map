# 지도 첫 구현 설계·구현 계획

날짜: 2026-10-08 · 상태: 설계 승인 · 지도 표시 우선 순서 변경 승인 · 실제 Git 브랜치: main
기준: [승인된 첫 구현 명세](spec.md)의 M-01~05·MC-01~05, FR-001·006~009.
setup-plan 출력의 001-map-discovery는 기능 식별자이며 실제 Git 브랜치 생성은 하지 않았다.

## Summary

Next.js 한 앱에서 네이버 지도 화면과 시험용 조회·SSE·마감 API를 제공한다.
모집 상태와 모달 선택을 분리하여 마감된 일반 마커만 제거하고 선택한 모집은 회색으로 유지한다.
사용자는 브라우저 두 개로 마감을 조작·관찰하며 SDD와 TDD 한 사이클을 경험한다.

## Technical Context

- TypeScript, Next.js App Router, React. 현재 Node 24.12.0 / npm 11.6.2 확인.
  Next.js 16 계열의 설치 시점 안정 패치와 호환 React·TypeScript를 선택하고 lockfile로 고정한다.
- 지도: NAVER Maps JavaScript API v3 직접 사용. 추가 React 지도 래퍼는 사용하지 않는다.
- 상태: React state/reducer + fetch + EventSource. 조회 자원이 하나여서 별도 캐시 라이브러리 없이 시작한다.
- 데이터: 단일 Node 프로세스의 메모리 시험 저장소. 서버 재시작 시 초기화한다.
  globalThis에 저장소 한 개를 유지하여 개발 중 모듈 재평가로 구독과 데이터가 분리되지 않게 한다.
  다중 프로세스·서버리스 배포·영속 저장은 이번 설계에 포함하지 않는다.
- 테스트: Vitest(규칙·동기화), Testing Library(모달), Playwright(실제 HTTP/SSE와 두 세션).
- 로컬 반응형 웹: 1440×900, 390×844. 정상 연결의 마감 반영은 매회 2초 이내.
- 설계 승인 후 지도 표시 Green까지 진행했다. 실행 상태와 남은 작업은 tasks.md 및 quickstart.md에 기록한다.

## 화면과 책임

- 상단: 서비스 이름·시험 데이터 표시·실시간 연결/갱신 상태.
- 본문: 네이버 지도와 모집 마커. 빈 영역 안내는 지도 이동을 막지 않는 작은 안내로 표시.
- 상세: 제목·음식·시각·수령/식사 방식·계산 방식·상태·비활성 참여 버튼.
  모달에는 이름·닫기 버튼·키보드 포커스 관리·Escape 닫기를 제공한다.
  모바일은 화면 내에 맞추고 내용이 길면 모달 내부를 스크롤한다.
- 로컬 시험 도구: 모집별 마감·데이터 초기화. 일반 참여 기능과 구분한다.
- 네이버 지도 어댑터는 지도·마커 생성/갱신/해제만 담당한다.
  지도 객체를 업무 상태의 원본으로 사용하지 않는다. SDK 로딩은 중복 호출을 합치고 오류 시 재시도한다.
- 공개 데이터에는 실제 주소·정확한 만남 장소·채팅 필드 자체를 만들지 않는다.

## 데이터 흐름과 실패 처리

1. 화면 진입 시 공개 시험 모집을 조회하고 SSE 연결을 시작한다.
2. SSE 서버는 구독 등록 직후 현재 세대(epoch)·버전(revision)을 ready 이벤트로 보낸다.
   ready 수신 때도 재조회하여 최초 조회와 구독 사이에 발생한 변경을 복구한다.
3. 시험 마감 API가 모집 상태를 저장하고 버전을 올린 후 changed 이벤트를 보낸다.
4. 브라우저는 알림의 최신 버전 이상인 조회 결과를 받아 화면 상태를 한 번에 갱신한다.
   요청 중 알림이 오면 재조회 필요 표시를 남겨 후속 조회한다. 오래된 응답은 최신 상태를 덮지 않는다.
5. 공개 조회는 모집 중 목록과 현재 선택한 ID의 공개 상세를 함께 반환한다.
   선택한 모집이 마감돼도 상세를 확인할 수 있지만 일반 마감 목록은 제공하지 않는다.
6. 선택 해제 시 닫힌 모집의 예외 마커도 즉시 제거한다. 데이터 갱신 때문에 모달을 강제로 닫지 않는다.
7. 연결 오류 시 기존 데이터를 유지하고 재연결 안내. 재연결 ready 후 최신 조회가 성공해야 안내를 해제한다.
   조회 실패는 1초→2초→최대 5초 간격으로 재시도하며 수동 재시도도 제공한다.
   연결이 끊긴 동안 뒤늦게 끝난 요청으로 정상 상태를 표시하지 않는다.
8. 서버 세대가 바뀌면 버전 비교를 초기화하고 새 조회를 사용한다. 이전 연결·선택의 응답은 무시한다.
   연결 종료·화면 해제 때 구독, heartbeat, 재시도 타이머, 진행 중 요청을 정리한다.
9. 선택한 ID가 존재하지 않으면 마감으로 추측하지 않고 모달에 조회 불가를 표시한다.
   시험 초기화는 동일 ID 집합을 사용하여 정상 마감 시나리오와 구분한다.

## Constitution Check

- 착수 전: 첫 구현 명세 승인 확인. 다른 기능·운영 정책까지 승인한 것으로 확대하지 않는다.
- 설계 후: 승인 범위와 MC 연결 확인. 지도 표시 구현·검사 완료, 사용자 Green 리뷰 대기. 커밋·푸시는 별도 지시를 따른다.
- 사용자 설계 승인 및 후속 화면 배치·연남동 시작 위치 승인 확인. tasks.md 순서대로 실행한다.
- 각 단위는 Red 결과 리뷰 → Green 결과 리뷰 → Refactor 결과 리뷰를 유지한다.
  테스트 실패는 의도한 동작 실패여야 하며 import/설정 오류를 Red 근거로 삼지 않는다.
- AI_LOG 갱신과 사용자 코드 설명·커밋/푸시 별도 지시 원칙을 유지한다.

## Project Structure

문서: plan.md, research.md, data-model.md, contracts/map-api.md, quickstart.md.
작업 목록: tasks.md. 아래 구조 중 지도 표시 소스를 생성했으며 서버·SSE 등은 후속 작업이다.

- src/app/: 페이지, 레이아웃, 스타일, api/map 및 api/dev 라우트
- src/features/map/: 순수 표시 규칙, 조회/SSE 동기화, 지도 어댑터, 화면·모달
- src/server/: 시험 데이터·저장소·SSE 구독 관리
- tests/: unit, integration, e2e

## 한계·검증 방법

[quickstart.md](quickstart.md)에 실행·검증 절차를 둔다. SDK 대역 테스트 통과와 실제 지도 성공을 구분한다.
실제 서버에서 두 요청이 같은 저장소를 쓰는지 통합 검증한다. 공유가 실패하면 완료 처리하지 않는다.
시험용 변경 API는 명시적 로컬 시험 모드에서만 활성화하고 미설정 시 404를 반환한다.
루프백 바인딩·동일 Origin 검사·JSON POST만 허용한다. 이 설계로 공개 배포하지 않는다.
헌법 예외 없음. 영속 DB나 배포가 필요해지면 별도 설계한다.

## 승인된 지도 표시 우선 변경

사용자는 브레인스토밍 후 실제 네이버 지도를 먼저 띄우기로 선택했다.
Figma PC 메인 2:2를 시각 기준으로 사용하되 헤더와 검색 영역을 위로 이동한다.
https://www.figma.com/design/DLAopCpFgjiiAdyWuUL2z2?node-id=2-2

- 순서: 헤더 → 검색 영역 → 왼쪽 모집 목록 영역(PC 420px)·오른쪽 실제 지도.
- 시작 위치: 연남동. 시안의 예시 배경 지도는 실제 네이버 지도로 대체한다.
- 검색·로그인·목록 등 미구현 기능은 준비 중으로 표시한다. 시안의 인원·금액 정책을 구현하지 않는다.
- 첫 TDD 단위: SDK 키 누락·로드 성공·로드 실패·재시도·중복 로드 방지.
  Red는 계약만 있는 미구현 함수를 호출해 동작 실패를 확인하고, 사용자 리뷰 후 Green으로 진행한다.
- SDK 성공 이후 화면의 로딩·오류/재시도, 실제 지도 생성·이동·확대/축소를 별도 단위로 검증한다.
- 모바일은 첫 단계에서 준비 중인 목록 영역을 지도 위에 간결하게 배치하고 가로 넘침을 막는다.
  PC 시안에 없는 세부 모바일 디자인은 첫 화면 리뷰에서 확인한다.
