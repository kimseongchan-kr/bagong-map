# 기능 명세: 배공맵 디자인 시스템 — Button 첫 사이클

**작성일**: 2026-10-12
**상태**: 명세 및 설계·순차 실행 승인(2026-10-12) — 각 Red·Green·Refactor 리뷰 유지
**기능 식별자**: `008-design-system` · 별도 기능 브랜치 미생성
**입력**: 배공맵 전용 디자인 시스템을 Storybook과 연결하고, Button 하나의 전체 과정을 경험한 뒤 사용자의 이해를 확인하고 나머지를 옮긴다.
**요구사항 출처**: 이번 대화의 추가 개발 기반 요청. PRD의 신규 제품 기능으로 간주하지 않는다.

## 목적·범위·비목표

개발자는 기존 Figma의 디자인 기준을 실제 화면과 컴포넌트 예시에서 함께 사용한다.
사용자와 멘토는 예시, 동작 검증, 설계 이유를 보고 재사용 구조를 이해할 수 있어야 한다.
이번 완료 단위는 Button 하나이며, 나머지 컴포넌트의 이관은 사용자의 이해 확인 이후 별도로 정한다.

- 포함: Button에 필요한 디자인 토큰, 공통 Button, Storybook의 상태 예시와 사용 문서, 지도 오류 화면의 ‘다시 시도’ 버튼 교체, 관련 검증과 이해 확인.
- 제외: Input·Badge 등 다른 컴포넌트의 구현, 화면 전체 버튼 교체, 별도 패키지 배포, Storybook 공개 배포, Figma 수정·자동 동기화, 로그인·SSE 등 제품 기능 추가.
- 기존 지도 코드는 `4d36713`으로 커밋했다. SDK 로더·지도 정리·재시도 설명은 확인했으며, 테스트 코드 설명만 사용자 지시로 추후 확인한다. 이 예외는 이번 Button 작업의 리뷰·설명 절차에 확대 적용하지 않는다.

- Figma에는 Primary·Secondary·Ghost의 3가지 스타일과 Default·Hover·Focus·Disabled·Loading의 5가지 상태가 있다.
- Button은 표시와 조작을 담당하고, 사용하는 화면이 실행할 동작·로딩 여부·비활성화 조건을 전달한다. Button은 지도 SDK나 업무 규칙을 소유하지 않는다.
- 사용자는 함수 전달과 역할 분리를 자기 말로 설명했다. 이는 개념 이해 확인이며 아직 작성하지 않은 코드의 설명 검증을 대신하지 않는다.
- 실제 적용 대상은 지도 오류 화면의 ‘다시 시도’ 버튼으로 합의했다.

## User Scenarios & Testing

### User Story 1 — 디자인과 상태를 독립적으로 리뷰한다 (Priority: P1)

개발자와 리뷰어는 지도를 실행하거나 키를 설정하지 않고 공통 Button의 모양과 조작을 확인한다.

**우선순위 이유**: 실제 화면에 적용하기 전에 재사용할 컴포넌트의 기준을 독립적으로 검증한다.

**독립 검증**: Storybook에서 스타일·문구·로딩·비활성화 조건을 변경하고 마우스와 키보드로 조작한다.

**수용 시나리오**:

1. 예시를 열면 3가지 스타일 각각의 기본·호버·포커스·비활성·로딩 상태를 재현할 수 있다.
2. 활성 버튼을 클릭하거나 키보드로 한 번 실행하면 예시 동작이 한 번 실행된다.
3. Disabled 또는 Loading인 동안 마우스·키보드로 실행해도 예시 동작은 실행되지 않는다.
4. 로딩을 해제하고 비활성화도 해제하면 원래 문구와 실행 가능 상태로 돌아온다.

### User Story 2 — 실제 지도 화면에서 같은 Button을 사용한다 (Priority: P1)

방문자는 지도 로딩 실패 후 공통 Button으로 다시 시도하며 기존 오류·로딩·성공 흐름을 유지한다.

**우선순위 이유**: 문서용 예시와 제품에 쓰이는 컴포넌트가 동일하다는 실제 사용 근거를 만든다.

**독립 검증**: 지도 로딩 실패를 재현하고 ‘다시 시도’를 실행하여 성공과 재실패를 각각 확인한다.

**수용 시나리오**:

1. 지도 로딩이 실패하면 오류 안내와 이름이 ‘다시 시도’인 공통 Button을 표시한다.
2. 실행하면 기존처럼 오류 안내와 버튼이 사라지고 지도 로딩 안내로 전환된다. 로딩 버튼을 남기는 화면 변경은 하지 않는다.
3. 재시도가 성공하면 지도를 표시하고, 재실패하면 새 오류 안내와 재시도 버튼을 표시한다.
4. 이 교체로 다른 버튼·검색·로그인 등의 동작이나 지도 생성·해제 규칙이 바뀌지 않는다.

### User Story 3 — 설계를 설명한 뒤 다음 컴포넌트로 확장한다 (Priority: P2)

사용자는 디자인 토큰, Button의 역할, 실제 화면과 예시의 연결, 검증 결과를 설명하고 다음 작업을 결정한다.

**우선순위 이유**: 사용자가 리뷰와 검증을 담당하며 설명하지 못하는 코드는 커밋하지 않는 협업 원칙을 지킨다.

**독립 검증**: 사용자가 작성된 코드와 실행 화면을 보며 설명하고, AI는 실제 동작·테스트와 비교해 보완점을 기록한다.

**수용 시나리오**:

1. 사용자가 토큰을 공유하는 이유와 Button이 SDK를 알 필요가 없는 이유를 설명한다.
2. 실행 함수와 로딩 상태를 각각 전달하는 이유, 비활성·로딩 상태의 입력 차단, 키보드 검증을 설명한다.
3. 이해 확인이 완료되기 전에는 다른 컴포넌트로 확장하지 않는다. 완료 후에도 다음 대상은 사용자와 합의한다.

### Edge Cases

- Loading과 Disabled가 동시에 전달되면 처리 중 표시를 유지하고 실행을 차단한다. Loading만 해제해도 Disabled가 남아 있으면 실행할 수 없다.
- Button은 전달된 비동기 동작의 성공·실패로 로딩 상태를 스스로 추측하지 않는다. 실패 처리와 상태 전환은 사용하는 화면에서 책임진다.
- 비활성 상태에서는 마우스를 올려도 활성 버튼의 호버 표시가 나타나지 않는다. 활성 버튼은 키보드 포커스를 눈으로 구분할 수 있어야 한다.
- 한국어 문구가 길거나 화면이 좁아도 문구가 잘리거나 주변 요소와 겹치지 않는다.
- 제출을 지정하지 않은 버튼이 입력 양식 안에 있어도 의도치 않은 제출이 발생하지 않는다.
- Storybook의 Loading 예시는 지도 재시도 화면의 실제 로딩 전환과 구분하여 설명한다.

## Requirements

### Functional Requirements

- **DS-FR-001 — 디자인 기준**: Button에 쓰이는 Figma 색상·간격·글자 기준을 공통 이름으로 관리하고, 실제 화면과 예시가 같은 정의를 사용한다. 첫 토큰 범위는 아래 가정을 따른다.
- **DS-FR-002 — 스타일과 상태**: 3가지 스타일·5가지 상태를 재현한다. 호버와 포커스는 실제 조작에 따라 나타나야 하며, 단순히 상태 이름만 바꾼 정적 그림으로 검증을 대신하지 않는다.
- **DS-FR-003 — 실행 경계**: Button은 전달받은 동작만 연결한다. 업무 요청, 재시도, 권한 판단, 로딩 상태의 소유는 사용하는 화면에 둔다. 활성 상태의 한 번 실행은 동작을 한 번 호출한다.
- **DS-FR-004 — 로딩과 비활성화**: 둘 중 하나라도 활성화되면 추가 실행을 차단한다. 로딩 중에는 ‘처리 중…’을 표시하고 보조 기술에도 원래 행동과 처리 중 상태를 전달한다. 중복 요청의 서버 측 방지까지 보장하는 것으로 설명하지 않는다.
- **DS-FR-005 — 키보드와 의미**: 버튼의 이름과 역할을 보조 기술로 확인할 수 있고, 활성 버튼은 Tab으로 접근하여 Enter·Space로 실행할 수 있어야 한다. 제출 동작은 명시적으로 선택했을 때만 수행한다.
- **DS-FR-006 — 리뷰 환경과 문서**: Storybook에서 문구·스타일·로딩·비활성화를 조절하고 실제 호버·포커스를 확인할 수 있어야 한다. 사용 목적, 상태별 예시, 사용 방법, 책임 분리의 이유, Figma 링크, 키보드 검증 방법을 한국어로 제공한다. 지도 SDK·지도 키·업무 서버 없이 Button 예시를 실행할 수 있어야 한다.
- **DS-FR-007 — 실제 적용과 호환성**: 지도 오류 화면의 ‘다시 시도’에 같은 Button을 사용한다. 지도 재시도와 로딩·성공·재실패 흐름은 User Story 2를 따른다. 해당 버튼의 디자인 변경 외에 다른 화면 요소를 일괄 변경하지 않는다.
- **DS-FR-008 — 단계별 리뷰와 이해 확인**: 합의한 작업 단위의 Red → 사용자 리뷰 → Green → 사용자 리뷰 → Refactor → 사용자 리뷰를 유지한다. 토큰·설정·문서에는 적절한 구조·빌드·문서 검사를 적용한다. 구현 완료 후 사용자의 직접 설명과 이해 확인을 마친 뒤 다른 컴포넌트로 확장한다. 커밋·푸시는 각각 별도 지시를 따른다.

### Key Entities

- **디자인 토큰**: 디자인 값에 이름을 부여한 공통 기준. 기본 색상과 이를 참조하는 사용 색상의 관계를 보존한다.
- **Button**: 문구·스타일·실행할 동작·로딩 여부·비활성화 여부를 받아 표시와 조작을 담당하는 요소.
- **Story**: 같은 Button에 특정 입력과 예시 동작을 제공해 상태를 독립적으로 확인하는 사례.

새 운영 데이터·서버 인터페이스·저장 구조는 추가하지 않는다. 구체적인 코드 인터페이스와 도구 설정은 명세 승인 이후 설계한다.

## Assumptions

다음은 명세 확정 시 채택한 기본안이다. 범위나 사용자 동작을 바꾸는 변경은 별도로 검토한다.

- 첫 토큰 이관은 Button에 필요한 `color/brand`, `brandHover`, `brandSoft`, `white`, `ink`, `line`, `focus`, `disabled`, `onDisabled`와 그 기본 색상, `space/8`, `space/12`, Button 글자 기준부터 진행한다. 나머지 토큰·글자 스타일의 전체 이관은 후속 컴포넌트에서 확장한다.
- 원본 예시의 크기는 180×48, 모서리는 12, 글자는 Noto Sans KR·14·굵기 700·줄 높이 21이다. 원본 비교 예시는 이 크기를 사용하고, 실제 적용에서는 문구와 부모 영역에 맞춰 폭을 조절한다. 긴 문구에는 줄바꿈과 높이 확장을 허용한다. 별도 크기 변형이나 아이콘 전용 버튼은 이번 범위에 넣지 않는다.
- 브랜드색 `#e65c32`, 포커스색 `#2463eb` 등 원본 토큰을 보존한다. 단, 승인된 대비 보완에 따라 Primary 버튼 전용 기본 배경 `#c94620`와 더 어두운 호버 토큰을 추가한다. 일반 크기의 활성 버튼 글자는 배경과 최소 4.5:1 대비를 확보한다. 추가 디자인 변경이 필요한 문제가 나오면 관련 값을 임의로 바꾸지 않고 이유·대안을 제시해 결정한다.
- 공개 배포 대신 로컬에서 리뷰 가능한 문서와 예시를 완성한다. 사용자 이해 확인 후 포트폴리오 공개 방식은 별도 작업으로 정한다.
