# 기능 명세: 모집 생성과 조건 입력

**작성일**: 2026-10-06
**상태**: 초안 — 사용자 검토·승인 전
**브랜치**: 별도 기능 브랜치 미생성
**입력**: 노션 PRD v0.1을 기준으로 전체 범위를 기능별로 분해하라는 사용자 요청
**PRD 연결**: REQ-03, REQ-04 · AC-03

[전체 범위·원본·협업 원칙](../README.md)

## 목적·범위·비목표

모집자가 음식과 수령·식사 장소, 계산 방식과 마감 조건을 입력하여 공동 주문자를 모집한다.

- 포함: 모집 생성, 수령·식사 방식과 계산 방식 선택, 공개 위치와 정확한 장소 구분, 모집자 메뉴·금액과 목표 조건.
- 비목표·경계: 승인·취소·마감·금액 계산·채팅은 다른 기능에서 다룬다. 모집 생성 후 모집 정보 수정 범위와 참가자 재확인 정책은 아직 확정되지 않았다.

확정은 원본 PRD의 합의 내용이다. 제안·미정은 승인되지 않았다. 아래 시나리오와 SC는 확정 요구사항도 검증 가능한 문장으로 구체화한 검토용 제안이며, 실제 검증 통과를 의미하지 않는다.

## 사용자 시나리오와 검증

### 사용자 이야기 1 — 모집 등록 (P1)

로그인 모집자가 조건을 입력하고 공개 모집을 만든다.

**우선순위 이유**: 참가자가 찾을 수 있는 모집의 시작점이다.
**개별 검증**: 합의한 필수 필드의 유효한 값을 입력하여 등록하고 다시 조회한다. 공통 의존 기능 또는 합의한 시험 데이터를 준비한다. 이 시험만으로 서비스 전체 완료를 선언하지 않는다.

**수용 시나리오 — 검토용 제안**:

1. **주어진 조건**: 로그인 사용자와 유효한 필수 정보가 있을 때 **행동**: 모집을 등록하면 **기대 결과**: 생성된 모집이 지도와 공개 상세에서 확인된다. [AC-03]
2. **주어진 조건**: 등록된 모집이 있을 때 **행동**: 상세를 새로고침하면 **기대 결과**: 선택한 수령·식사 방식과 계산 방식이 유지된다. [AC-03]

### 사용자 이야기 2 — 주문 방식과 모집 조건 선택 (P1)

모집자가 두 가지 수령·식사 방식과 두 가지 계산 방식을 각각 선택한다.

**우선순위 이유**: 모집 참가자의 기대와 목표 충족 기준을 정한다.
**개별 검증**: 두 축의 네 조합으로 시험 모집을 등록하고 선택값을 확인한다. 공통 의존 기능 또는 합의한 시험 데이터를 준비한다. 이 시험만으로 서비스 전체 완료를 선언하지 않는다.

**수용 시나리오 — 검토용 제안**:

1. **주어진 조건**: 등록 양식을 작성 중일 때 **행동**: 수령·식사 방식과 계산 방식을 선택하면 **기대 결과**: 두 선택을 독립적으로 지정하고 참가자가 신청 전에 확인할 수 있다. [REQ-04]

### 경계 사례

- 필수값 누락·음수 금액·목표 인원 미달 범위·이미 지난 시각: 유효성 조건과 오류 안내는 OPEN-03에서 정한다.
- 모집자 금액 또는 인원만으로 목표가 이미 충족됨: 등록 즉시 마감 여부는 OPEN-04에서 정한다.
- 중복 등록·저장 실패: 한 번만 생성하고 실패를 성공으로 표시하지 않는 안은 PRD의 제안이다.
- 정확한 장소 변경·계산 방식 변경·모집자 메뉴 수정: 생성 후 수정 권한과 참가자 동의·합계 영향은 별도 검토한다.

## 요구사항

### 기능 요구사항

- **FR-001 · 확정**: 음식·장소·금액·마감 조건을 입력하여 모집을 생성한다. 필수 필드 세부 목록은 미정이다. 출처: REQ-03.
- **FR-002 · 확정**: 수령·식사 방식은 각자 가져가기 또는 함께 먹기 중 하나를 선택한다. 출처: REQ-04.
- **FR-003 · 확정**: 계산 방식은 개별 메뉴값 또는 전체 금액 균등 분할 중 하나를 선택한다. 출처: REQ-04.
- **FR-004 · 확정**: 공개용 대략 위치와 승인자용 정확한 장소를 구분한다. 출처: REQ-06.
- **FR-005 · 확정**: 수동 마감을 기본으로 하며 자동 마감은 선택 사항이다. 출처: REQ-09.
- **FR-006 · 확정**: 개별 메뉴 자동 마감은 승인 음식값 합계, 균등 분할 자동 마감은 승인 인원을 기준으로 한다. 모집자를 포함하며 배달비는 목표 음식값 합계에서 제외한다. 출처: REQ-10.
- **FR-007 · 제안**: 가게 이름·음식 설명·메뉴와 금액·예상 시간·배달비·마감 시각·목표 조건·안내를 입력한다. 링크·최대 인원은 선택 항목으로 제안한다. 출처: PRD 7장.
- **FR-008 · 제안**: 모집 하나당 가게 하나로 제한하며 실제 가격·판매 여부·최소 주문액은 모집자가 외부 배달앱에서 확인한다. 출처: PRD 4장·7장.

### 주요 데이터 개념

- 모집: 모집자, 가게·음식, 방식, 시간, 상태, 조건. 상세 필드는 미정이다.
- 장소 정보: 대략 위치와 정확한 장소·안내. 두 정보의 공개 대상을 구분한다.
- 모집자 주문 내용: 개별 메뉴의 본인 메뉴·음식값, 균등 분할의 전체 음식값을 표현하는 안이다.

## 완료 조건

### 측정 가능한 검증 결과 — 검토용 제안

- **SC-001**: 유효한 등록 모집이 지도·상세에서 확인되고 새로고침 후 선택값이 유지된다. [AC-03]
- **SC-002**: 두 축의 네 조합 모두 등록·조회 시 선택한 방식이 유지된다. [REQ-04를 구체화한 검증 제안]
- **SC-003**: 입력 검증 규칙 확정 후 각 경계 입력이 합의한 결과로 처리된다. 현재는 검증 대기다. [OPEN-03]

이 기능의 검증 결과는 관련 PRD AC로 추적한다. 제품 성과 지표의 목표값·관찰 기간은 OPEN-07에서 별도로 결정한다.

## 가정·의존성·호환성

- 002의 로그인, 001의 공개 조회, 005의 마감 조건과 연결된다. 공개 지도에 노출할 필드는 001과 함께 확정한다.
- 이 명세는 새 프로젝트에 적용한다. 기존 비공개 프로젝트의 코드·데이터를 가져오거나 기존 사용자 데이터를 이전하는 요구는 포함하지 않는다.
- 한국어 PC·모바일 웹 지원은 전체 제약이다. 기술 선택은 승인된 명세의 후속 설계에서 다룬다.
- 각 단계에 사용자 리뷰·검증을 포함한다. 현재 구현 계획·작업 목록·제품 코드는 작성하지 않았다.
