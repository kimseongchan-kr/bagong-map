# 기존 기능 명세 점검 결과

점검일: 2026-10-06 · 상태: 사용자 검토 대기

## 후속 반영 상태

- REV-01: 사용자 정정 승인 후 README의 constitution 상태와 공통 절차를 수정했다.
  constitution 링크·TDD 단계별 리뷰·직접 코드 설명·AI_LOG 안내와 사용자 지시의 brainstorming 원칙을 반영했다.
  문서 링크·형식 검사 통과. 수정 결과의 사용자 최종 리뷰는 대기 중이다.
- REV-02~03: 정정안 승인 후 아직 미반영. 현재 작업은 사용자 지시에 따라 REV-01만 다룬다.
- REV-04~07: 기존 검토·결정 대기 상태를 유지한다.

아래는 최초 점검 시점의 근거와 제안이다. 이후 수정 결과는 위 반영 상태에서 구분한다.

## 대상과 한계

노션 PRD와 미정 사항을 다시 조회하고 전체 범위 문서, 기능 명세 7개,
품질 체크리스트 7개를 현재 constitution 초안에 대조했다.
기능별 `plan.md`·`tasks.md`·제품 코드는 없으므로 설계·코드·테스트 품질 검사는 수행하지 않았다.
사용자 검토 전 명세를 고치거나 제품 규칙을 확정하지 않았다.
이 파일은 검토 결과이며 새로운 제품 요구사항이나 구현 승인 문서가 아니다.

- [전체 범위](README.md)
- [현재 constitution 초안](../.specify/memory/constitution.md)
- [PRD 원본](https://app.notion.com/p/3ecae6a75ec081ee98dff6ef22372d13)
- [미정 사항 원본](https://app.notion.com/p/3ecae6a75ec081ef90a1dab9cb881b51)

## 결론

초안은 PRD의 핵심 기능과 REQ-01~14를 다루고 있으며,
확정·제안·미정과 사용자 승인 상태를 구분한 점은 유지할 수 있다.
그러나 constitution 변경을 반영하지 못한 설명, 권한 예외가 모호한 문장,
검증 조건과 결정 항목의 구체성 부족이 남아 있어 설계·구현 준비 완료로 판단하지 않는다.

## 확인된 문서 문제와 개선안

### REV-01 · Constitution 상태와 공통 작업 절차가 오래됐다

- 대상: [README 협업 원칙](README.md), [README 다음 단계](README.md).
- 근거: README는 constitution을 기본 템플릿이라고 설명한다.
  현재 파일은 이미 `1.0.0-draft`로 작성·보완되어 있다.
  공통 절차에는 이후 합의한 TDD의 단계별 리뷰, 사용자 직접 코드 설명,
  AI_LOG 기록 규칙이 반영되어 있지 않다. 커밋 형식도 여전히 제안으로 적혀 있다.
- 영향: 명세 작성 시점의 요약을 현재 작업 규칙으로 오해할 수 있다.
- 개선안: 오래된 상태를 수정하고 공통 작업 원칙의 기준은 constitution에 연결한다.
  명세마다 원칙 전체를 복사하기보다 링크와 준수 확인 항목을 사용한다.
  constitution은 여전히 정식 제정 전 초안임을 명시한다.
- 구분: 문서 사실·합의 반영 문제. 새로운 제품 규칙의 결정은 필요하지 않다.

### REV-02 · 지도 명세의 승인 전 제한에 모집자 예외가 빠졌다

- 대상: [001 FR-003](001-map-discovery/spec.md).
- 근거: “승인 전에는 정확한 장소와 그룹 채팅을 공개하지 않는다”는 문장이
  방문자·신청자를 한정하지 않는다. 002는 모집자 또는 승인 참가자의 접근을 허용한다.
- 영향: 모집자도 별도 참가 승인 전에는 본인이 입력한 장소를 보지 못하는 것으로 읽힐 수 있다.
- 개선안: 공개 조회·신청자 접근 제한이라는 범위를 명시하고 모집자와 승인 참가자의 접근은
  002/007을 따른다고 연결한다. 재승인·취소 후 접근은 OPEN-05로 남긴다.
- 구분: 기능 간 문장 일관성 문제. 재승인 접근 정책을 여기서 결정하면 안 된다.

### REV-03 · AI가 추가한 범위와 제안의 출처가 더 명확해야 한다

- 대상: [007 비목표](007-chat-place/spec.md), 기능별 경계 사례와 가정.
- 근거: 007은 “채팅으로 합의한 내용을 주문 데이터에 자동 반영하지 않는다”를
  조건 없는 비목표로 기술한다. PRD는 합의한 변경의 실제 데이터 반영 절차를 미정으로 둔다.
  자기 모집 신청, 재신청, 세션 만료, 주문 완료 되돌리기 등 일부 검토 항목도 AI가 추가했다.
- 영향: 원본 합의와 AI 제안의 경계가 본문의 확정·제안 표기만으로는 완전히 드러나지 않는다.
- 개선안: 자동 반영 제외는 AI 제안으로 표시하고 수동 반영 절차와 구분한다.
  각 추가 항목에 원본 출처 또는 AI 추가 제안임을 표시한다.
  새 프로젝트에 기존 코드·데이터를 가져오지 않는 문구는 범위 가정으로 유지하고
  별도의 영구적인 금지 원칙으로 해석하지 않는다.
- 구분: 출처·상태 표시 개선과 사용자 제안 검토가 모두 필요하다.

### REV-04 · 실제 주문과 주문 완료 표시 사이의 검증 경계가 남아 있다

- 대상: [004 취소 시나리오와 FR-004](004-participation/spec.md),
  [005 주문 완료 시나리오](005-recruitment-lifecycle/spec.md).
- 근거: 004의 확정 요구는 실제 주문 후 채팅 협의지만 수용 시나리오는 주문 완료 표시를 기준으로 한다.
  PRD도 두 시점의 차이와 분쟁을 자동 판단하지 않는다고 밝힌다.
- 영향: 실제 주문이 끝났지만 표시하지 않은 상태의 취소 요청을 어떻게 처리하는지
  시스템 테스트의 기대 결과를 확정할 수 없다.
- 개선안: 제품 원칙인 실제 주문 이후 협의와 시스템이 관찰하는 표시 상태를 구분한다.
  불일치 시 안내·처리 범위는 사용자 결정 항목으로 남기고 테스트로 임의 판단하지 않는다.
- 구분: 기존 PRD의 불확실성. AI가 해결한 것으로 표시하지 않는다.

### REV-05 · 승인 인원·음식값·부담액과 접근 권한의 상태별 정의가 필요하다

- 대상: [004 참여 상태](004-participation/spec.md), [005 자동 마감](005-recruitment-lifecycle/spec.md),
  [006 계산 대상](006-cost-sharing/spec.md), [002 권한](002-auth-access/spec.md),
  [007 접근 수명](007-chat-place/spec.md).
- 근거: 재승인 대기 음식값 제외는 확정되어 있다.
  승인 인원 포함, 표시 부담액 계산 대상, 장소·채팅 접근은 명세에 결정 대기로 남아 있다.
- 영향: 음식값 합계와 인원·부담액을 같은 값처럼 취급하면 기능 간 결과가 달라질 수 있다.
- 개선안: 대기·승인·재승인 대기·취소 요청·취소의 각 상태에 대해
  음식값 포함/인원 포함/부담액 표시/장소 접근/채팅 접근을 한 표로 정하고
  모든 관련 명세에서 동일한 기준을 참조한다.
- 구분: 확정 내용 재사용과 OPEN-01·02·05 등의 사용자 결정이 필요하다.

### REV-06 · 검증 조건의 추적과 구체성을 보완해야 한다

- 대상: 모든 기능 명세의 FR·SC·시나리오, [전체 범위 추적 표](README.md),
  기능별 `checklists/requirements.md`.
- 근거: 모든 PRD REQ 번호가 등장하지만 각 FR에서 어떤 SC·시나리오로 검증하는지
  명시한 표는 없다. 예를 들어 001의 REQ-04 확인 동작과 FR-005 위치 거절 제안은
  메타데이터 또는 SC에서 직접적인 연결이 부족하다.
  “합의한 규칙에 일치”, “모든 시나리오 통과”만으로는 미정 규칙을 테스트로 옮길 수 없다.
- 영향: 번호가 있다는 사실을 전체 요구사항의 검증 준비 완료로 오해할 수 있다.
- 개선안: 기능별로 FR → PRD REQ → 시나리오/SC → 관련 AC의 연결을 정리하고,
  미채택 제안·결정 대기·검증 대상 확정을 구분한다.
  AC-17의 전체 흐름과 AC-18의 동시 상태 검증은 기능별 결과와 별도로 관리한다.
  TDD 테스트 작성은 해당 검증 조건 승인 이후에 진행한다.
- 구분: 검증 준비 개선. 현재 체크리스트의 원본 참조 연결 체크는 부분 확인으로 읽어야 하며,
  상세 추적과 상태 점검 전 전체 연결 완료를 주장하지 않는다.

### REV-07 · 3개 질문 묶음은 실제 결정 3개를 의미하지 않는다

- 대상: 7개 기능 명세의 Q-01~03.
- 근거: 각 기능에는 세 묶음만 있지만 하나에 입력 필드·인원 상한·세션·운영 정책 등
  독립적인 결정이 여러 개 들어 있다. 현재 총 21개 결정 묶음이 남아 있다.
- 영향: 한 번의 답변으로 여러 정책을 일괄 승인했다고 오해하거나
  첫 기능과 무관한 결정을 한꺼번에 요구할 수 있다.
- 개선안: 기능 검토 시 관련 OPEN 항목을 한 가지씩 질문하고 결정 결과를 기록한다.
  최초 기능 설계에 필요한 결정과 후속 기능·공개 시험 운영 전 결정을 구분한다.
  목표·가격·마감·권한 등 핵심 규칙은 가정으로 메우지 않는다.
- 구분: 검토 방식 개선. 현재 미정 항목은 그대로 유지한다.

## 기계적인 문서 확인 결과

- 기능 명세 7개와 체크리스트 7개가 존재한다.
- 필수 문서 섹션과 로컬 문서 링크 검사 통과.
- 기능 명세 전체에서 REQ-01~14 참조 존재 확인.
- 모든 기능에서 사용자 승인 전 상태와 미정 결정을 유지한다.
- 구현 계획·작업 목록·제품 테스트는 미작성·미실행이다.
- 현재 constitution도 `1.0.0-draft`이며 이 검토로 정식 제정하지 않았다.

## 제안하는 다음 작업

1. 사용자와 REV-01~03의 문서 정정·출처 표시 개선 범위를 검토한다.
2. 승인한 정정만 반영하고 체크리스트도 실제 검토 수준에 맞춘다.
3. 전체 기능 분해와 AI 추가 제안을 검토한 뒤 첫 기능의 미정 사항을 한 가지씩 결정한다.
4. 기능 명세 승인 후에만 설계·검증 계획 단계로 이동한다.
5. specs 커밋은 포함 내용과 메시지를 별도로 검토한 뒤 진행한다.
