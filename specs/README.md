# 배공맵 전체 범위와 명세 안내

작성일: 2026-10-06 · 상태: 사용자 검토용 초안

## 목적과 기준 문서

서울의 배달 이용자가 지도에서 가까운 공동 주문자를 찾아 최소 주문 조건을 함께 충족하고, 필요한 음식과 비용을 부담한다. 1~2개월 내 포트폴리오용 첫 버전을 만들고 한 동네·대학가에서 시험 운영하는 것이 PRD의 목표다. 기간 내 구현 가능성은 설계와 작업 분해에서 검토한다.

- 요구사항 원본: [배공맵 PRD v0.1 — 검토용 초안](https://app.notion.com/p/3ecae6a75ec081ee98dff6ef22372d13)
- 미정 사항 원본: [미정 사항](https://app.notion.com/p/3ecae6a75ec081ef90a1dab9cb881b51)
- 원본 확인일: 2026-10-06. 원본의 마지막 수정일은 2026-10-01이다.

노션 PRD를 제품 기획의 기준으로 사용하고, 이 폴더는 기능별 동작과 검증 조건을 구체화한다. 자동 동기화되지 않으므로 요구사항 변경 시 원본과 명세의 차이를 검토한다. 충돌하면 조용히 한쪽을 채택하지 않고 사용자에게 확인한다. 이 문서 작성 승인은 구현 승인이나 PRD 제안 항목의 일괄 승인이 아니다.

## 협업 원칙

> 프로젝트에서는 동료: 작업을 맡기되 리뷰와 검증은 내가 하기.

공통 개발·리뷰 원칙의 기준 문서는 [constitution](../.specify/memory/constitution.md)이다. 현재 버전은 `1.0.0-draft`이며 정식 제정 전이다. 아래는 지금까지 합의한 작업 절차의 안내이며, 이 README의 수정이 constitution의 정식 제정이나 기능 명세 승인을 대신하지 않는다.

- 모든 작업은 constitution의 원칙 III에 따라 brainstorming으로 목적·범위·놓칠 수 있는 부분과 검증 방법을 함께 확인한다. 작은 작업은 짧게 논의하며, 이미 승인한 범위를 반복 승인받지 않고 새로운 선택과 범위 변경은 먼저 검토한다.
- 명세·설계·코드의 각 단계 결과를 사용자에게 제공하고 승인 후 다음 단계로 진행한다. AI 검증은 사용자 리뷰·직접 검증을 대신하지 않는다.
- 제품 동작은 합의한 작업 단위의 Red → Green → Refactor로 구현하며 단계별로 리뷰받는다. 문서 변경은 문서 검토로 확인한다.
- 코드 커밋 전 사용자가 직접 변경 목적·동작·선택 이유·예외·테스트를 설명한다. 설명 검토 후에도 커밋·푸시는 각각 명시적 지시가 필요하다.
- 맡긴 작업과 확인된 AI 오류·사용자 수정 방법은 [AI_LOG.md](../AI_LOG.md)에 기록한다.

문서는 한국어로 작성한다. 커밋 메시지는 constitution에 따라 `type(scope): 한국어 변경 내용` 형식을 사용하며 scope는 선택 사항이다. 전체 type 목록은 별도 확정 전이다.

## 전체 범위

### PRD 확정 사항

- Next.js 기반 한국어 반응형 웹, PC·모바일 브라우저 지원.
- 서울 지역 지도 탐색, 로그인 후 모집 생성·신청, 모집자 승인.
- 각자 가져가기 또는 함께 먹기, 개별 메뉴값 또는 전체 금액 균등 분할.
- 대략적인 모임 위치 공개, 승인 참가자에게 정확한 장소와 그룹 채팅 제공.
- 수동 마감 기본, 자동 마감 선택, 메뉴 수정·재승인·취소·주문 완료 표시.
- 모집자가 외부 배달앱에서 주문하고 참가자는 외부에서 직접 정산. 서비스는 부담 금액을 계산한다.

### 확정된 제외 범위

네이티브 앱, 내부 결제·송금, 별도 커뮤니티 게시판, 친구 추가, 정기 모임.

### 추가 제외 제안 — 사용자 승인 전

배달앱 자동 주문·가격 조회·주문 상태 동기화, 여러 가게를 한 모집으로 합산, 리뷰·평점·추천, 쿠폰 발급·보상·예치금. 모집당 가게 하나 제한도 제안이다.

## 기능 분해와 추적

번호는 문서 식별자이며 구현 순서를 확정하지 않는다. 명세의 FR은 로컬 요구사항 번호이고 PRD의 REQ·AC와 연결한다. 모든 기능의 승인 조건·설계·코드 검증이 끝나야 전체 사용자 흐름이 완성된다.

| 명세 | 범위 | PRD 요구사항 | PRD 완료 조건 | 주요 의존성 |
|---|---|---|---|---|
| [001 지도 탐색](001-map-discovery/spec.md) | 비로그인 지도·공개 상세 | REQ-01, REQ-06 | AC-01, AC-17 일부 | 지도 공급자, 공개 모집 데이터 |
| [002 로그인·권한](002-auth-access/spec.md) | 인증과 행동별 접근 | REQ-02, REQ-06, REQ-07 | AC-02, AC-05 | 로그인 공급자, 참여 상태 |
| [003 모집 생성](003-recruitment-creation/spec.md) | 모집 정보·방식·조건 | REQ-03, REQ-04 | AC-03 | 로그인, 입력·장소 정책 |
| [004 참여 관리](004-participation/spec.md) | 신청·승인·수정·취소 | REQ-05, REQ-11, REQ-12, REQ-14 | AC-04, AC-12~14, AC-18 일부 | 모집 상태, 권한, 합계 |

AC-17은 PC·모바일에서 탐색 → 등록 → 신청 → 승인 → 채팅 → 마감 → 주문 완료 → 분담액 확인의 통합 검증이다. AC-18은 참여·마감·합계가 동시에 바뀌는 교차 검증이다. 기능별 테스트만으로 두 조건의 완료를 선언하지 않는다.

## 공통 제약과 검토 항목

- 정확한 위치는 음식점이 아니라 수령·식사 장소다. 집 주소를 기본 공개 위치로 취급하지 않는다.
- 대기 금액·인원과 배달비는 자동 마감용 승인 음식값 합계에 넣지 않는다. 모집자는 인원과 음식값에 포함한다.
- 모집 중 승인 후 메뉴 수정은 재승인 대기로 전환하며 음식값은 합계에서 제외한다. 해당 인원의 자동 마감 인원 포함 여부는 승인 상태 규칙과 함께 확인한다.
- 자동 마감 이후 금액·인원이 줄어도 자동 재개하지 않는다.
- 주문 완료는 모집자의 직접 표시이며 외부 주문 사실·송금 완료의 자동 증명이 아니다.
- 정확한 장소가 공개 응답에 포함되지 않도록 하는 서버 권한 검증, 동시성·중복 요청 처리, 실패 복구, 위치 권한 거절 시 탐색 대안은 PRD의 비기능 제안이다. 구현 전에 채택 여부와 검증 조건을 확정한다.
- 계정·장소·메시지의 보관·삭제·탈퇴, 백업·신고 대응, 접근성·성능 목표는 별도 검토한다.

## 검토와 다음 단계

현재 산출물은 전체 범위와 기능별 명세 초안이다. 각 기능의 완료 조건은 검토용 제안이며 구현·테스트 통과를 표시하지 않는다. 다음 순서는 brainstorming으로 범위 확인 → 필요한 미정 사항 결정 → 기능 명세 승인 → 설계·검증 계획 승인 → 합의한 작업 단위의 TDD와 단계별 리뷰 → 사용자 직접 검증이다. 코드 커밋 전에는 직접 설명과 작업 로그 갱신을 확인하고, 포함 파일과 메시지를 검토받는다.

기능별 계획은 승인 이후 해당 폴더의 `plan.md`, 작업 목록은 `tasks.md`로 작성한다. 현재 동반 writing-plans 스킬은 설치 목록에 없으므로, 승인 이후 설치된 speckit-plan 절차와 프로젝트 컨벤션을 사용한다. 추가 스킬을 설치하지 않는다.

첫 검토 대상으로 001 지도 탐색을 제안한다. 공개 위치 정책과 입력 모집 데이터에 의존하므로 지도 공급자·공개 정보·위치 정밀도부터 확인한다. constitution은 기본 템플릿을 대체한 검토용 초안이며, 정식 제정과 각 기능 명세 승인은 별도 확인한다.

spec-kit의 현재 기능 포인터는 `001-map-discovery`로 설정했다. `.specify/feature.json`은 기존 규칙에 따라 Git 추적에서 제외되는 로컬 상태다. 기능 브랜치는 생성하지 않았으며 실제 Git 브랜치는 `main`이다. 다른 기능을 작업할 때는 해당 기능으로 포인터를 전환하고 경로를 확인한다.
